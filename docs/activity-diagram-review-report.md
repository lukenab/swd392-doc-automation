## Blocked use cases — questions for BA/PO

### UC-25 `UC-SPRINT-TASK-CLAIM` — BLOCKED — INSUFFICIENT SPECIFICATION

- **Reason:** AF-01 'The Developer withdraws before confirmation' refers to a confirmation step that the normal flow does not contain (NF1 opens and claims the task; NF2-NF4 are System steps). The point at which AF-01 can occur, and what the Developer confirms, are not specified.
- **Question:** Should the normal flow contain a confirmation step (for example 'System asks the Developer to confirm the claim' and 'Developer confirms the claim'), or should AF-01 be removed?
- **Question:** If a confirmation step is added, does EX-01 (another Developer claims first) apply before or after the confirmation?

### UC-27.4 `UC-SUBTASK-COMPLETE` — BLOCKED — REQUIREMENT CONFLICT

- **Reason:** AF-01 'The User restores a completed subtask to an incomplete state' conflicts with precondition 3 'The subtask is not already complete' and with NF1 'Selects an incomplete subtask'. AF-01 is an actor-initiated action that can only start from a state the preconditions exclude, so it cannot be drawn without violating the Use Case Description.
- **Question:** Should restoring a completed subtask be a separate use case (for example 'Reopen Subtask'), or should precondition 3 be relaxed so that this use case covers both directions?
- **Question:** If both directions stay here, which steps does the restore path share with the normal flow (validation, EX-01)?

## Modelling conventions applied

- Authentication is a precondition only; Log In appears only in UC-SIGN-IN.
- Partitions name the responsibility, not the account type: Guest, User, Project Owner, Product Owner,
  Developer, System Administrator, System, Email Service, Identity Provider. A YAML step written as
  "Acting as the Product Owner/Developer" is placed in that role's partition.
- Every action carries a trace comment (`' [NF2, POST1, BR-..., AF-01.1, EX-01]`) that the validator checks
  against the Use Case YAML. GUIDE-7.3 marks a System reject/report action added because the YAML names an
  exception but not its outcome.
- Each exception ends with one System reject/report action. Paths with the same outcome share one
  Activity Final (see "End-node policy" below).
- An alternative flow resumes after the step where it was raised, or returns to the step it re-performs;
  cancelling and terminal alternative flows end the activity.
- Validation failures that the YAML does not describe are not drawn; they are listed as observations.

## End-node policy (audit 2026-10-03)

UML 2.5.1 allows several ActivityFinalNodes; the first one reached ends the whole activity. The team
convention applied after the audit: (1) paths with the same outcome share one Activity Final, through merge
nodes; (2) separate Activity Finals are kept only for different outcomes, and each one is explained in the
header comment of the source; (3) when different outcomes occur on several nested branches (UC-01, UC-02,
UC-30), one shared Activity Final is used, because separate finals would need duplicate finals for the same
outcome; the last action on each path states the outcome; (4) UC-13 keeps two finals for the same outcome,
because merging them would require drawing NF5 twice. No Flow Final is used. Details per end node:
`docs/activity-diagram-audit-report.md`.

## Preconditions contradicted by an alternative flow or exception

When an exception or alternative flow describes a state that a precondition excludes, and the System can detect
that state, it is drawn as a defensive System check and recorded as an observation. When an alternative flow
needs the actor to start from a state that the preconditions exclude (UC-27.4), the use case is blocked as a
requirement conflict, because drawing it would contradict the Use Case Description.

## A4 legibility method

The effective guard-text size is the SVG guard font (14 px = 10.5 pt) multiplied by the scale needed to fit the
diagram into a 16.5 x 20.5 cm text area (A4 portrait, 2.25 cm margins, room for the caption). Diagrams below
6 pt are marked `needs-manual-review`; all diagrams stay portrait and no landscape exception is used.

## Deviation from the original guideline

Section 6 of the earlier guideline named the actor partition "User". The Stage 2 instruction requires
responsibility-specific partitions, so the guideline now uses the role names above. The PowerShell renderer
scripts/render-activity-diagrams.ps1 is superseded by scripts/activity_diagrams.py and left unchanged.

## PlantUML layout limitations found

- `repeat while ... is (...) not (...)` loses its guard labels with diamond conditions, so loops use `while`.
- `elseif` with vertical ifs draws hexagons, so multi-way choices are nested binary decisions.
- `switch` and `goto` do not render usable swimlane diagrams.
- A decision branch that switches partition right below the diamond is crossed by its own flow line; branches
  are arranged so that the cross-partition branch leaves the diamond horizontally.
